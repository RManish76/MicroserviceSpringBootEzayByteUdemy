*5* limt the wait time
    currently for all MS where circuitbreaker is not implemented(loans & cards), if we made any request to that MS then
    client will wait for the response it does not matter how much time it takes.
    Means if there is slow response from any MS for any reason we would have an open thread which will
    be occupied just waiting for the response.
    Idealy in MS if after sometime any request should timeout if response is taking a lot of time.
    We have seen that in gatewayserver we have implemented the circuitbreaker, so in case of accounts MS
    if the requests take more than 1sec the circuitbreaker in gatewayserver will kill the request and
    will fallback to fallback mechanism which we configured. 
    Because by default the circuitbreakers are configured to wait for 1sec on any request for response.

    But we may not be using the circuitbreaker throughout our MSs. So to handle these problem in other
    places like loans and cards MS, where we are not using the circuitbreaker pattern, we need to 
    configure that timeout configuration so that the gateway server or any other MS, ther are not 
    going to wait for the response for a long time.

    doc for timeout: https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/http-timeouts-configuration.html

        So we need to add the configs in application.yml as per the doc.
            connect-timeout --> in miliSec this is the which takes to makes connection to a MS
                        For example the gatewayserver made request to loan MS but to reach the loan MS
                        or we can say that to establish the connection between gatewayserver and loan MS
                        is time we are considering here.
            response-timeout --> as name sussgest max wait time for response

        so add below in application.yml
                spring:
                    cloud:
                        gateway:
                        httpclient:
                            connect-timeout: 1000
                            response-timeout: 5s

    So this timout which we added is global means whatever request will flow thorugh the gatewayserver
    this timout will be applicable except if we have circuitbreaker configured for any particular
    request.
    Means if there are both circuitbreaker and defaulttime like above then circuitbreaker config will have
    have higher precedence.

    In doc if we see we can define the timeout like above for each route/api request using yml or java
    And also if we notice in same section of doc there metion about -1 timeout.
    This timeout is for that if we want that for any particular api should not be bound by gloabl timeout
    which we configured then we'll can mention timeout as -1 this will exempt that api from global
    timeout means for that request gatewayserver will wait untill we kill the request manually or 
    we have dedicatly configured a timeout for that api link.


*6* Retry pattern
    The retry pattern wil make configured multiple retry attempts when a service has temporarily failed.
    This pattern is very helpful in the scenarios like network disruption where the client request may
    successful after a retry attempt.

    The key components and considerations of implementing the Retry pattern in microservices:

        Retry Logic: Determine when and how many times to retry an operation. This can be based on factors
                        such as error codes, exceptions or response status.

        Backoff Strategy: Define a Strategy for delaying retries to avoid overwhelming the system or
                            exacerbatling the underlying issue(like fixed interval is not good). This
                            strategy can involve gradually increasing the delay between each retry, known
                            as exponential backoff.

        Circuit Breaker Integration: Consider combining the Retry pattern with the Circuit Breaker pattern.
                            If a certain number of retries fail consecutively, the circuit can be opened to
                            prevent further attempts and preserve system resources.

        Idempotent Operations: Ensure that the retried operation is idempotent, meaning it produces the same
                                result regardless of how many times it is invoked. This prevents unintended
                                side effects or duplicate operations.

*11* Rate LIMITTER PATTERN

    The Rate Limiter pattern in MS is a design pattern that helps control and limit the rate of incoming requests
    to a service or API. It is used to prevent abuse, protect system resources, and ensure fair usage of the service.

    In a microservices architecture, multiple services may depend on each other and make requests to communicate.
    However, unrestricted and uncontrolled requests can lead to performance degradation, resource exhaustion and
    potential denial-of-service(DoS) attacks. The Rate Limiter pattern provides a mechanism to enforce limits on
    the rate of incoming requests.

    Implementing the Rate Limiter Pattern helps protect miscroservices from being overwhelmed by excessive or
    malicious requests.

    When a user surpasses the permitted number of requests within a designated time frame, any additional
    requests are declined with an HTTP 429 - Too Many Requests status. The specific limit is enforced based
    on a chosen strategy, such as limiting requests per session, IP address, users, or tenant.
    The primary objective is to maintain system availability for all users, especially during challenging
    circumstances. This exemplifies the essence of resilience.
    Additionally, the Rate Limiterpattern proves benefical for providing services to users based on their
    subscription tiers.
    For instance, distinct rate limits can be defined for basic, permium, and enterprise users.

        redis-rate-limiter.replenishRate=int --> number token to be filled per second in the bucket.
        redis-rate-limiter.burstCapacity --> number of max toker per second allowed in a bucket.(keep sum of all previous non used token)
        redis-rate-limiter.requestedTokens --> number of token as cost of each request.

        A steady rate is accomplished by setting the same value in replenishRate and burstCapacity.
        Temporary bursts can be allowed by setting burstCapacity higher than replenishRate.
        In this case, the rate limiter needs to be allowed some time between bursts (according to replenishRate),
        as two consecutive bursts results in dropped requests (HTTP 429 - Too Many Requests).
        The following listing configures a redis-rate-limiter:

            Rate limits below 1 request/s are accomplished by setting replenishRate to the wanted number of requests,
            requestedTokens to the timespan in seconds,
            and burstCapacity to the product of replenishRate and requestedTokens.
            For example, setting replenishRate=1, requestedTokens=60, and burstCapacity=60 results in
            a limit of 1 request/min.

*14* BULKHEAD PATTERN
        The Bulkhead pattern in software architecture is a design pattern that aims to improve the resilience and
        isolation of components or services within a system. It draws imspiration from the concept of bulkheads in
        ships, which are physical partitions that prevent the flooding of one compartment from affecting others,
        enhancing the overall stability and safety of the vessel.

        In the context of software systems, the Bulkhead pattern is used to isolate and limit the impact of failures or high
        loads in one component from spreading to other components. It helps ensure that a failaure or heavy load in one
        part of the system does not bring down the entire system, enabling other components to continue functioning
        independently.

        Bulkhead pattern helps us to allocate limit the resources which can be used for specific services.
        So that resource exhaustion can be educed.

        The Bhulkhead pattern is particularly useful in systems that require high availability, fault tolerance,
        and isolation between components. By compartmentalizing components and enforcing resource boundaries,
        the Bulkhead pattern enhances the reilience and stability of the system, ensuring that failures or heavey
        loads in one area do not bring down the entire system.

        For example:
            we have two api endpoing /myAccount and /myCustomerDetails in accounts MS.
            And the /myAccount is doing some limited work and not depended on any other service or MS.
            where as the /myCustomerDetails endpoint is dependent on some ther MS and services.

            Without bulkheads or in general case the /myCustomerDetails will consume more thread and resource compared to /myAccount
            so if few more request come to /myCustomerDetails there is chance that there'll be no resource available
            for /myAccount which also consume less resource.

            With Bulkhead we 'll assign minimum resource to each endpoint like sepration we do with docker containers
            and even if /myCustomerDetails is going to consume more resource at least assigned resource will be
            available to /myAccount endpoint to process the request it have.

        Note: Inside the spring cloud gateway we don't have bulkhead support as of now
            we can only use resilience4j to use the bulkhead.
             we can go to resilience4j doc link https://resilience4j.readme.io/docs/getting-started-3
             and look for annotation realted to Bulkhead and we see the way we can implement the bulkhead in the MS.
