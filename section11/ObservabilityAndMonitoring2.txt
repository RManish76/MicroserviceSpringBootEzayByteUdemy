*2* Metrics
   Using logs alone we can not monitor our applications. Because with the help of events, logs we can only
   try to understand what happened under a specific scenario or under a specific method.
   With the help of the logs, we can't understand what is the overall health of my accounts microservice
   or any other microservice.

   So to properly monitor the MS, we need to understand metrics details like what is the CPU usage, what
   is the memory usage, what is the headp dump usage, what are the threads connections errors.
   So that's why we need to make usre we are aslo collecting the metrics and using the sasme metrics.
   We need to build the dashboards so that operation team, they can always monitor our MS.

   Metrics are numerical measurements of an application's performance, collected and aggregated at regular
   intervals. They can be used to montior the application's health and performance, and to set alerts or
   notifications when thresholds are exceeded.
      We will use springBoot Actuator, Micrometer, Prometheus & Grafana to acheive the metrics.

      1. Actuator - Actuator is aminly used to expose operational information about running application
                     health, metrics, info, dump, env, etc. It uses HTTP endpoints or JMX beans to enable
                     us to interact with it.
                     We can goto path /actuator/metrics and we will be see many metrics that can help you
                     to monitor the MS instance.
                     Mannually going to each path and checking the health status is not feasible.

                     So we need something which can aggregate all the metric details for us.
                     Now we component already inside the open-source. The component is Prometheus
                     But it cannot understand the actuator responses because it's in JSON.

                     So we would another component in middle which can convert the actuator JSON into
                     which Prometheus can under. And that component is MicroMeter.

      2. MICROMETER - Micrometer automatically exposes /actuator/metrics data into something our monitoring
                     system can understand. All we need to do is include that vendor-specific micrometer
                     dependency in our application. Think SLF4J, but for metrics.
                        SLF4J --> helps to implement multiple logging framework with very less effort.
                           it is a facade.

                     weblink: https://micrometer.io/

      3. Prometheus - The most common format for exporting metrics is the one used by Prometheus, which is
                        "an open source systems monitoring and alerting toolkit". Just as Loki aggregates
                        and stores event logs, Prometheus does the same with metrics.

                        weblink: https://prometheus.io/

      4. Grafana -   Grafana is a visualization tool that can be used to create dashboards and charts from
                     Prometheus data.
                     Why we need Grafana again, because Prometheus has certain limitations.
                     We cannot build very complex dashboards and we cannot create alerts and notifications
                     with the Prometheus alone.
                     When we integrate Prometheus with Grafana, we can build a lot of dashboards and apart from
                     dashboards we can also create alerts and notifications.


      To implement all of these we need to add dependency realted to micrometer and prometheus in our project.

      4>> Distributed Tracing In Microservice

         Event logs, health probes and metrics offer a wealth of valuable information for deducing the
         internal condition of an application.
         Nevertheless, these sources fail to account for the distributed nature of cloud-native applications.
         Given that a user request often traverses multiple applications, we currently lack the means to
         effectively correlate data across application boundaries.

         Distributed tracing --- is a technique used in microservices or cloud-native applications to understand
         and analyze the flow of requests as they propagate across multiple services and components. It helps is
         gaining insights into how requests are processed, identifying performance botttlenecks, and
         diagnosing issues in complex, distributed system.
         
         >> One possible solution to address this issue is to implement a straightforward approach where a
            unique identifier, known as a correlation ID, is generated for each request at the entry point of
            the systems. This correlation ID can then be utilized in event logs and passed along to other relevant
            services involved in processing the request. By leveraging this correlation ID, we can retrieve all log
            messages associated with a specific transaction from multiple applications.

         >> Distributed tracing encompasses three primary concepts:

            Tags: Tags serve as metadata that offer supplementary details about the span context, including the
                  request URI, the username of the authenticated user, or the identifier for a specific tanant.
                  (like application name will tell the current log is from which application)

            Trace ID: A trace denotes the collection of actions tied to a request or transaction,
                        distinguished by a Trace ID. It consists of multiple spans that span across various
                        services.
                        (like we have correlation id, using this we can trace to all places where the request traveled)

            Span ID:  A span represents each individual stage of request processing, encompassing start and end
                        timestamps, and is uniquely identified by the combination of trace ID amd span ID.

                        (span id uniques to each application which will tell that this request where travling
                        inside a MS ).
            So all three we will have in every request we recive along with the request from the MS.



            For example: id can be like below and so below will look like for all MS as example
                     [Tag,Trace ID, Span ID]

                     gatewayserver MS - [gatewayserver, 29cdbe2e21bc, 259d5208]
                     accounts MS      - [accounts, 29cdbe2e21bc, 61fd3a92]
                     loans MS         - [loans, 29cdbe2e21bc, 9e5b7f81] - logger statement 1
                                      - [loans, 29cdbe2e21bc, 9e5b7f81] - logger statement 2
                     cards MS         - [cards, 29cdbe2e21bc, 8f4b7a76] - logger statement 1
                                      - [cards, 29cdbe2e21bc, 8f4b7a76] - logger statement 2
